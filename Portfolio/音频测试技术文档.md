音频测试技术文档 —— Cytus2 风格音频菜单系统

> 被测系统：基于 Wwise 2025.1 + Unity 2022.3 的交互式音频菜单系统
> 范围：音频系统技术拆解 / 可测试性分析 / 测试策略 / 风险管控 / 质量度量 / 改进建议

---

## 1. 文档目的

本文从音频测试工程师视角，对被测音频系统进行完整的技术拆解与质量分析。音频测试的难点在于：**问题往往不产生于单一层，而是 UI 事件 → 引擎封装 → Wwise 中间件 → 最终听感 之间的边界上**。因此本项目的质量工作重心不是"测 UI"，而是"理解音频链路，在每一层边界设置观测点"。

文档同时沉淀测试策略、风险清单与工具化思路，作为后续版本回归与需求迭代的质量基线。

---

## 2. 被测系统技术拆解

### 2.1 音频链路分层

```
[UI 事件] MainMenuUI / CharacterSelectUI / SongSelectUI / SettingsUI
      ↓ 调用
[封装层] WwiseIntegration（PostEvent / SetSwitch / SetRTPC / LoadBank / 回退 AudioSource）
      ↓ 调用
[管理器] AudioSystemManager（Bank 加载 / 音乐状态机 / 角色主题 / 预览控制 / UI 音效）
      ↓ 调用          MenuManager（界面状态机 + 转场音频时机）
[引擎]   AkUnitySoundEngine（P/Invoke → AkUnitySoundEngine.dll）
      ↓
[Wwise] Event → Actor-Mixer/Music → Bus（Music Bus / SFX Bus）→ Main Audio Bus → 系统输出
```

### 2.2 Wwise 工程结构（中间件侧被测对象）

```
Main Audio Bus（Master，System 设备）
├── Music Bus          ← Music_Volume（RTPC，0–100）
└── SFX Bus            ← SFX_Volume（RTPC，0–100）

MenuMusic = Music Switch Container（Switch Group: Menu_Music）
├── MainMenu      (Playlist，Loop=Infinite)
├── CharacterSelect（嵌套 Music Switch Container，Switch Group: Character_Theme）
│   ├── paff / neko / Cherry / ... / Non（各角色 Playlist，Loop=Infinite）
├── SongSelect    (Playlist)
└── InGame        (Playlist)

SoundBank：Init / Music / SongPreviews / UI
```

### 2.3 关键交互机制（测试需验证的行为契约）

| 机制 | 实现 | 测试关注点 |
|---|---|---|
| 界面切换音乐 | `Menu_Music` 一次 Post、后续 SetSwitch 换段 | 各状态间切换是否无声/正确换段 |
| 角色主题曲 | `Character_Theme` Switch 驱动的嵌套容器 | 切角色是否即时/无串音/循环 |
| 歌曲预览 | `PlaySongPreview`：Wwise 事件优先，PlayingID 精确停播，失败回退 AudioSource | 精确停播、无叠加、回退是否可用 |
| 音量 | `Music_Volume`/`SFX_Volume` RTPC 控制 Bus Volume | 0–100 单调性、独立控制、持久化 |
| 转场音频时机 | MenuManager 在"退出界面/到达界面"两个时点触发 | 音频与转场动画的时序一致 |

## 3. 可测试性分析

音频系统的可测试性取决于**控制点是否清晰、观测点是否充分**：

- **控制点（可控输入）**：所有事件名 / Switch 名 / RTPC 名以字符串配置在 Inspector 与数据资产中，可通过改数据驱动不同路径。
- **确定性**：界面切换由 `MenuManager` 单一状态机驱动，流程可脚本化复现。
- **降级路径**：Wwise 事件缺失时回退 `AudioSource`，构成一条可单独验证的降级链路。
- **难点 1——时序敏感**：多管理器 `Start` 顺序不确定、转场存在"音频窗口"，易产生首帧静音/时序竞态，需反复进出场景验证。
- **难点 2——听感主观**：切歌是否"顺滑/在拍上"无法断言式校验，需结合 Wwise Profiler 的转场事件与人工听测双轨验证。
- **难点 3——命名易碎**：Game Sync 名是大小写敏感字符串，是静默失效的高发点，需工具化核验（见 §6）。

## 4. 测试策略与范围

### 4.1 分层测试模型

1. **冒烟（Smoke）**：冷启动有声、主菜单曲循环、四界面可进出、无红错。作为每次构建的准入项。
2. **功能（Functional）**：§2.3 的机制契约逐条验证（对应 F- 用例集）。
3. **音频表现（Audio 表现）**：切歌无爆音、无串音、转场顺滑、预览精确停止（对应 P-EXP- 用例集）。
4. **性能（Performance）**：启动时间、Bank 内存、长时间运行稳定性（对应 PERF- 用例集）。
5. **兼容（Compatibility）**：分辨率、平台 Bank、Wwise 版本一致性（对应 CMPT- 用例集）。
6. **回归（Regression）**：每次音频/Wwise/打包改动后，重点复跑"静音类、命名类、时序类"历史缺陷用例。

### 4.2 跨层定位方法论（本项目核心方法）

音频缺陷的高发位置在**层与层的边界**，定位策略：

- **跨端对比**：Wwise 走带（Transport）正常 ≠ Unity 运行时正常。二者不一致时，问题通常在"总线层级/输出设备/RTPC 作用域/Bank 同步"等集成层——这是 Wwise 走带无法暴露的。
- **生成产物反查**：音频行为异常时，优先反查 `Init.bnk` / `Init.json` / `SoundbanksInfo.json`，核对对象层级、ObjectPath、音频设备、Game Parameter 是否存在。
- **日志/Profiler 双轨**：Unity Console（含 `[Wwise]` 降级日志）+ Wwise Profiler（Event/Game Object/RTPC 轨迹）对齐时间轴。
- **数据-工程一致性**：CharacterData/SongData 里的事件名/Switch 名与 Wwise 工程逐项比对（大小写、拼写、是否真的存在于对应 Bank）。

## 5. 测试环境与观测工具

| 工具 | 用途 |
|---|---|
| Unity Editor（Play 模式） | 功能/交互回归，界面流程脚本化 |
| Unity Profiler | 启动耗时、内存、GC |
| Wwise Profiler | Event/Game Object/音乐转场/RTPC 实时轨迹（跨层定位主工具） |
| Wwise Transport（走带） | 隔离"工程配置问题"与"引擎集成问题" |
| Console `[Wwise]` 降级日志 | 引擎初始化、事件/Switch/RTPC 缺失告警 |
| 工程内编辑器工具（PreviewLinker / DataEditorWindow / AudioSceneSetup） | 批量生成测试数据、一键搭音频场景，降低测试造数成本 |

## 6. 工具化质量保障（对测试效率与质量的投入）

- **命名一致性核验（建议工具）**：数据资产中的 Event/Switch/RTPC 名与 Wwise 工程（通过 WAAPI 或生成清单 `SoundbanksInfo.json`）自动比对，杜绝"静默失效"类缺陷进入测试。
- **一键出包/回归脚本（建议工具）**：固化"保存场景 → 同步 Bank → Build"链路，保证每次回归基于一致基线，避免"场景未保存/ Bank 陈旧"这类环境性假缺陷。

---

## 7. 关键质量风险清单

| 风险 | 失效表现 | 等级 | 规避手段 |
|---|---|---|---|
| Bus 层级错误（平级/No_Output） | 全静音 | P0 | 构建后冒烟听声 + Init.json 层级核验 |
| RTPC 作用域 / 未设置 | 音量不可控 | P1 | 全局重载 + 启动强制应用 + Profiler 查看 RTPC |
| Game Sync 命名不一致 | 静默失效 | P1 | §6 命名核验工具 |
| 转场音频时序 | 预览被误停 / 主题曲不恢复 | P1 | 时序回归用例 + 转场动作慢速复现 |
| Bank 同步陈旧 | 新旧行为不一致 | P1 | 固化同步流程，版本号比对 |
| 大 Bank 同步加载 | 启动卡顿 | P2 | 性能基线 + 流式/异步改造建议 |
| 多管理器初始化顺序 | 首帧静音 | P2 | 起始阶段静音/出声窗口用例 |

## 8. 质量度量

- **功能用例通过率**：F- 系列全量通过为发布准入。
- **缺陷分级**：P0（静音/崩溃）/ P1（功能失效）/ P2（体验）口径统一。
- **回归基线**：历史缺陷清单（含根因）作为回归必跑集合，防止"修 A 破 B"。
- **听感主观项留痕**：音频表现类用例记录"切歌转场事件是否命中、有无爆音报告"，保留评审记录。

---

## 9. 对该系统后续版本的质量建议

1. **性能方向**：`Music.bnk`/`SongPreviews.bnk` 体积大且启动同步加载，建议评估流式加载 / `LoadBankAsync` / 按角色按需加载，并建立加载耗时基线。
2. **可测性方向**：为多管理器初始化顺序问题引入可注入的初始化协调点，消除首帧时序竞态对测试的干扰。
3. **工具方向**：落地 §6 两个工具（命名核验、一键出包回归），把人工易错点转为自动化门禁。
4. **兼容矩阵**：固化"Windows/Mac/Android + Wwise 版本"的 Bank 生成与真机验证清单，覆盖平台差异导致的 Bank/路径问题。
5. **需求迭代配合**：新增角色/曲目（内容侧）上线时，走"命名核验 → 冒烟 → 功能 → 表现 → 回归"的准入流程，测试前置到数据合入阶段而非成品阶段。

---

## 10. 结语

本项目作为 Unity + Wwise 交互式音频的完整样例，其质量保障的核心不在于用例数量，而在于**对音频链路的逐层理解**与**跨层观测能力**。通过跨端对比、生成产物反查、命名与数据一致性核验等手法，能够在缺陷进入听感之前将其定位到具体层级与根因，这正是音频测试工程师的核心价值。
